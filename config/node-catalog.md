# Orchestration Node Catalog

Generated by a read-only documentation pass over the orchestration engine at
`c:/AI_projects/scout`. Source of truth for config **shape** is
`shared/orchestrationTypes.ts` (the `*NodeConfig` types); source of truth for
**behavior** (validation, output, side effects) is each node's handler in
`lib/orchestrations/nodes/*.ts`, dispatched by `lib/orchestrations/engine.ts`.

This file and `config/node-catalog.json` are the first files under a new
top-level `config/` directory — there was no existing `/config` or
`/services` convention in this repo prior to this pass.

Sixteen `NodeType` values exist (`shared/orchestrationTypes.ts` line ~71):
`trigger, workflow, data_capture, ai_extraction, ai_task, knowledge_search,
condition, human_approval, notification, variable, data_formatter, api_call,
database, file_parser, for_each, end`. `trigger` and `end` are pseudo-nodes
(start/finish) handled inline in `engine.ts`, not separate handler files.
All 16 are documented below in that order.

---

## Trigger (`trigger`) — pseudo-start node

Entry point of an orchestration; publishes the trigger payload (manual input,
chatbot message, schedule tick, inbound email, or HTTP/API call) into the
execution context.

- **Handler**: none — inline in `engine.ts`'s `executeNodeByType()` and
  `findTriggerNode()`/`getTriggerType()`.
- **Config** (`TriggerNodeConfig`):
  | Field | Type | Required | Notes |
  |---|---|---|---|
  | `type` | `"trigger"` | yes | discriminant |
  | `triggerType` | `manual\|chatbot\|schedule\|email\|http_api` | yes | drives node-compatibility checks for the rest of the graph |
  | `schedule` | `{ cron?, timezone? }` | no | only meaningful for `triggerType: "schedule"` |
- **Validation**: none in the node itself; `node-compatibility.ts` uses
  `triggerType` to reject interactive nodes (`data_capture`, `human_approval`,
  `workflow`, `file_parser`) when the trigger is automated
  (schedule/email/http_api).
- **Output**: always succeeds — `{ ...triggerData, matchedPhrase,
  matchedIntent, trigger: { input, timestamp, startedBy, startedAt,
  matchedPhrase, matchedIntent }, _system: { triggeredBy, executionId } }`.
- **Side effects**: none — reads `execution.triggerData` already loaded by
  the caller.
- **Permission gating**: none at node level. Who/what can invoke the
  orchestration is controlled entirely at the trigger-definition level via
  `ChatbotTriggerConfig.allowedRoles` / `allowedUsers`
  (`shared/orchestrationTypes.ts`), enforced in
  `lib/orchestrations/chatbot-trigger-matcher.ts` — not in this node's path.
- **Risk tier**: low — Structural pseudo-node; no side effects of its own.

## Workflow (`workflow`)

Executes an existing Scout guided (browser-recorded) workflow via the
standard guided-workflow executor, with optional wait-for-completion. The
actual step-by-step run happens client-side, driven by the interactive Scout
Player (`public/scout-orchestration-player.js`) in the end user's own
browser, which reports back through the `/continue` API route — this handler
just kicks off / tracks the server-side execution record.

A previous "browser-automation mode" (Puppeteer launching a real, visible
browser server-side when `targetUrl` was set) existed early on but was never
used in practice and has been removed. `targetUrl` is now purely
informational, passed through to the execution context.

- **Handler**: `lib/orchestrations/nodes/workflow-node.ts`
- **Config** (`WorkflowNodeConfig`):
  | Field | Type | Required | Notes |
  |---|---|---|---|
  | `type` | `"workflow"` | yes | |
  | `workflowId` | `string` | TS-optional, runtime-required | must be a UUID; handler throws if blank/malformed |
  | `workflowVersion` | `number` | no | unused by this handler |
  | `targetUrl` | `string` | no | informational only; falls back to the workflow's `targetAppName` if unset |
  | `waitForCompletion` | `boolean` | no | polls until the workflow finishes |
  | `inputMapping` | `Record<string,string>` | yes | maps workflow inputs to context expressions |
  | `outputMapping` | `OutputMappingField[]` | no | **declared but never wired up — see Surprising Findings** |
  | `continueOnFailure` | `boolean` | yes | swallow failures into `{error, failed:true}` output |
  | `timeout` | `number` | no | ms; default 300000 |
  | `triggerPhrases` | `string[]` | no | if set, node is skipped (not failed) on phrase/intent mismatch |
  | `autoFillFromDataCapture` | `boolean` | no | not read by this handler |
  | `autoAdvancement` | `boolean` | no | not read by this handler |
- **Validation**: trigger-phrase mismatch → soft skip; missing `workflowId` →
  throw; non-UUID `workflowId` → throw.
- **Output (success)**: `{ executionId, workflowId, workflowTitle, status,
  steps, duration, ...output }`.
- **Output (failure, continueOnFailure=true)**: `{ error, failed:true, ... }`.
- **Side effects**: delegates to `lib/guided-workflows/executor`
  (`executeGuidedWorkflow` / `waitForWorkflowCompletion`), which records
  server-side execution state. No LLM calls.
- **Permission gating**: no execution-level check.
- **Risk tier**: medium — triggers execution of a guided workflow (which can perform real actions via the client player), but no longer drives a privileged, unattended server-side browser session.

## Data Capture (`data_capture`)

Client-run node type: the interactive Scout Player
(`public/scout-orchestration-player.js`) executes this step directly in the
end user's browser (showing a capture/review overlay and confirming page
data), then reports completion back through the `/continue` API route.

- **Handler**: none server-side. `lib/orchestrations/nodes/data-capture-node.ts`
  used to implement this via a Puppeteer-carried browser page, but that relied
  entirely on the removed "browser-automation mode" of the Workflow node
  (see above) and was never used in practice, so it was deleted along with
  Puppeteer as a dependency. `lib/orchestrations/engine.ts`'s `"data_capture"`
  case now returns a clear failure if this node type is ever reached outside
  an interactive, client-driven execution (e.g. from a scheduled trigger),
  since there is no server-side executor for it.
- **Config** (`DataCaptureNodeConfig`): unchanged — still a valid node type
  for interactive/client-driven orchestrations; see `shared/orchestrationTypes.ts`.
- **Risk tier**: n/a server-side (no server handler); the client-side capture/review UI runs in the end user's own browser.

## AI Extraction (`ai_extraction`)

Uses the configured LLM provider to extract structured data (predefined
schema, a runtime chat instruction, or both) from an input value/template,
optionally pausing to ask the chat user for missing mandatory fields.

- **Handler**: `lib/orchestrations/nodes/ai-extraction-node.ts`
- **Config** (`AIExtractionNodeConfig`):
  | Field | Type | Required | Notes |
  |---|---|---|---|
  | `type` | `"ai_extraction"` | yes | |
  | `extractionMode` | `predefined\|instruction\|hybrid` | no | default `"predefined"` |
  | `inputType` | `email\|document\|text\|variables` | no | declared but not branched on |
  | `input` | `string` | no | preferred input-text source (interpolated) |
  | `inputSource` | `string` | no | legacy single variable path, used only if `input` is blank |
  | `prompt` | `string` | no | extra instruction, defaults generically |
  | `clarificationTimeoutMinutes` | `number` | no | default 15, floored at 1 |
  | `fields` | `Array<{key,type,description?,required?}>` | no | preferred source of mandatory-field checks |
  | `schema` | `Record<string,unknown>` | yes | field descriptors; also mandatory-field source if `fields` absent |
  | `outputVariable` | `string` | yes | defaults to `"extracted"` if falsy |
- **Validation**: input must resolve non-empty; instruction/hybrid modes
  require a non-empty runtime instruction; LLM response must parse as JSON;
  `schema` entries marked `required` must at least be present as a key
  (`validateAgainstSchema`); mandatory fields (from `fields` or required
  schema entries) must have a *meaningful* value — if missing, pauses for
  clarification on chatbot triggers, throws on all other trigger types.
- **Output (success)**: `{ [outputVariable]: extractedData }`.
- **Output (paused)**: `{ success:true, paused:true,
  outputHandle:"clarification", output:{[outputVariable]: partialData},
  clarification:{missingFields, message, questions, timeoutMinutes,
  expiresAt, fieldDefinitions} }`.
- **Side effects**: one LLM call (`getLLMProvider().generate_answer`). No DB
  writes in this handler.
- **Permission gating**: none.
- **Risk tier**: low — LLM call only; no external side effects beyond the model call itself.

## AI Task (`ai_task`)

Runs an arbitrary LLM generation/transformation task (summarize, draft,
rewrite, etc.) using a configured instruction, a live chat message, or both,
against optional context content, returning text or structured JSON.

- **Handler**: `lib/orchestrations/nodes/ai-task-node.ts`
- **Config** (`AITaskNodeConfig`):
  | Field | Type | Required | Notes |
  |---|---|---|---|
  | `type` | `"ai_task"` | yes | |
  | `instructionMode` | `static\|chat\|hybrid` | yes | where the instruction comes from |
  | `instruction` | `string` | required for static/hybrid | optional persona text even in chat mode |
  | `input` | `string` | no | interpolated template for context content |
  | `outputFormat` | `text\|json` | yes | controls prompt shape & parsing |
  | `outputFields` | `AITaskOutputField[]` | required (non-empty) when `outputFormat="json"` | |
  | `outputVariable` | `string` | yes | defaults to `"aiTask"` |
  | `clarificationTimeoutMinutes` | `number` | no | **declared but not read — chat-mode clarification hardcodes a 15-minute expiry instead** |
- **Validation**: static mode needs `instruction`; hybrid needs a non-empty
  combined instruction; chat mode resolves a runtime instruction from the
  live chat message (or, after a clarification resume, from
  `${outputVariable}.instruction`) — if still empty, throws on non-chatbot
  triggers or pauses asking "What would you like me to do?" on chatbot
  triggers; JSON output format requires ≥1 `outputFields` entry; LLM JSON
  response must parse as an object.
- **Output (success)**: `{ [outputVariable]: string|object,
  [outputVariable+"Meta"]: {provider, model, instructionMode, instruction} }`.
- **Output (paused)**: `{ success:false, paused:true, clarification:{...} }`
  — note `success:false` here, unlike AI Extraction's `success:true` on
  pause.
- **Side effects**: resolves `companyId` (DB lookup on
  `company_target_applications` from `targetAppId`) to select a possibly
  company-scoped LLM provider; one LLM call.
- **Permission gating**: none.
- **Risk tier**: low — LLM call only; no external side effects beyond the model call itself.

## Knowledge Search (`knowledge_search`)

Runs a retrieval-only query against the company/target-app's RAG knowledge
base (`RetrievalEngine`) and returns ranked passages plus citations — no LLM
synthesis here (that's AI Task's job downstream).

- **Handler**: `lib/orchestrations/nodes/knowledge-search-node.ts`
- **Config** (`KnowledgeSearchNodeConfig`):
  | Field | Type | Required | Notes |
  |---|---|---|---|
  | `type` | `"knowledge_search"` | yes | |
  | `query` | `string` | yes | interpolated template |
  | `topK` | `number` | no | default 5, clamped to [1,20] |
  | `outputVariable` | `string` | yes | defaults to `"knowledgeSearch"` |
- **Validation**: `query` must be non-empty after evaluation; `companyId`
  must resolve (preferentially derived from `targetAppId` via DB lookup — "a
  chatbot is always scoped to one target app, never company-level" — else
  falls back to a direct `companyId`); `userId` must resolve from
  `_system.triggeredBy`/`trigger.startedBy`.
- **Output**: `{ [outputVariable]: formatted source text,
  [outputVariable+"Chunks"]: raw chunks, [outputVariable+"Citations"]:
  citations, [outputVariable+"Meta"]: {query, resultCount} }`.
- **Side effects**: DB read to derive `companyId`; calls
  `RetrievalEngine.retrieve(...)` against the knowledge/vector store. No LLM
  generation call.
- **Permission gating**: none role-based; scoped by companyId/targetAppId
  (tenant isolation).
- **Risk tier**: low — Read-only retrieval against the knowledge base.

## Condition (`condition`)

Evaluates one or more variable comparisons (with and/or chaining) and routes
to the `"true"` or `"false"` output handle. Pure routing — no context
mutation.

- **Handler**: `lib/orchestrations/nodes/condition-node.ts`
- **Config** (`ConditionNodeConfig`):
  | Field | Type | Required | Notes |
  |---|---|---|---|
  | `type` | `"condition"` | yes | |
  | `conditions` | `Array<{variable, operator, value?, logicAfter?, caseSensitive?}>` | yes | `operator` ∈ `ConditionOperator` (equals, not_equals, contains, not_contains, contains_any, contains_all, not_contains_any, greater_than, less_than, exists, not_exists, empty, not_empty); `logicAfter` default `"and"`; `caseSensitive` default `false` |
- **Validation**: `conditions` must be non-empty, else returns
  `{success:false, error:"No conditions defined"}` (not thrown). Evaluated
  strictly left-to-right, pairwise, via each condition's own `logicAfter` —
  no grouping/precedence.
- **Output**: `{ success:true, outputHandle: "true"|"false" }` — no `output`
  object; context is never mutated.
- **Side effects**: none — pure in-memory evaluation.
- **Permission gating**: none.
- **Risk tier**: low — Pure in-memory branching logic; no side effects.

## Human Approval (`human_approval`)

Pauses the orchestration and requests a human approve/reject decision,
creating an approval record and emailing the approver a review link.

- **Handler**: `lib/orchestrations/nodes/human-approval-node.ts`
- **Config** (`HumanApprovalNodeConfig`):
  | Field | Type | Required | Notes |
  |---|---|---|---|
  | `type` | `"human_approval"` | yes | |
  | `approverEmail` | `string` | yes | variable-expression capable |
  | `title` | `string` | yes | also the email subject / node execution label |
  | `description` | `string` | no | |
  | `fields` | `Array<{name,label,type,options?,editable,defaultValue?}>` | no | rendered in the approval request & email |
  | `timeout` | `number` | no | minutes — **declared but not read/enforced anywhere in this handler** |
  | `escalationEmail` | `string` | no | **declared but not used anywhere in this handler** |
- **Validation**: `approverEmail` must evaluate non-empty and match
  `/^[^\s@]+@[^\s@]+\.[^\s@]+$/`, else throws.
- **Output (initial run — always pauses)**: `{ success:true, paused:true,
  output:{approvalId, approvalPending:true, approver, approvalUrl} }`.
- **Output (resume, `resumeAfterApproval`)**: `{ success:true, outputHandle:
  "approved"|"rejected", output:{...approvalResponse, approved, approvedAt,
  approvedBy, notes} }`.
- **Side effects**: writes a node-execution record (`createNodeExecution`);
  writes an approval record (`createApproval`); sends an email to
  `approverEmail` via `sendEmail()` (email failure is logged and swallowed —
  the node still pauses successfully); builds an approval URL from
  `NEXT_PUBLIC_APP_URL`.
- **Permission gating**: none at node level — `approverEmail` is whatever
  the author/an upstream variable configures; no role check on who may be
  named approver or who may act on the resulting approval URL from within
  this handler.
- **Risk tier**: medium — Sends a real email and creates a durable, actionable approval URL, but exists specifically as a safety gate on further action.

## Notification (`notification`)

Sends a notification through one or more channels — email, internal in-app,
Microsoft Teams, Slack, SMS, WhatsApp — with per-channel retry and optional
scheduled delivery. Supports legacy single-channel config and the newer
multi-channel `channels` config.

- **Handler**: `lib/orchestrations/nodes/notification-node.ts`
- **Config** (`NotificationNodeConfig`) — legacy `channel`/`recipient`/
  `subject`/`message`/`template` fields, or the structured `channels` object
  with per-channel sub-shapes (`email`, `internal`, `teams`, `slack`, `sms`,
  `whatsapp`), each carrying its own `enabled`, content fields, `delivery`
  (`mode: immediate|scheduled`, `scheduledAt`), and `retry`
  (`enabled`, `maxAttempts`, `delaySeconds`). See
  `shared/orchestrationTypes.ts` lines 250–397 for the full per-channel
  field list (recipients, subject/body, webhook URLs, action buttons,
  template names, etc.).
- **Validation**: at least one channel must be enabled; per channel —
  email needs `to`+`body`+`senderCredentialId`; internal needs `message` and
  at least one of users/roles/teams/groups that resolves to ≥1 active user;
  teams/slack need a valid `http(s)` webhook URL and `message`; sms needs
  recipients + message + a webhook URL (channel or
  `NOTIFICATION_SMS_WEBHOOK_URL`); whatsapp needs recipients, and
  `templateName` (approved_template) or `body` (session_message), plus a
  webhook URL; scheduled delivery needs a parseable future `scheduledAt`;
  retry `maxAttempts` clamped [1,10], `delaySeconds` clamped [0,300].
- **Output (success)**: `{ notificationSent:true, startedAt, completedAt,
  attemptedChannelCount, sentChannelCount, scheduledChannelCount,
  failedChannelCount, enabledChannels, channelResults:[{channel, status,
  attempts, sentAt?, scheduledFor?, error?, details?}] }`.
- **Output (failure)**: same shape with `notificationSent:false` and
  per-channel error details — output is still populated on failure.
- **Side effects**: `sendEmail()` for email; **INSERTs into
  `internal_notifications`** for the internal channel, after resolving
  recipients via reads across `users`, `user_company_roles`/`roles`, and
  optional `teams`/`team_members` (or `user_teams`) /
  `groups`/`group_members` (or `user_groups`) tables; outbound HTTP POST to
  configured webhook URLs for teams/slack/sms/whatsapp; per-channel retry
  with a fixed delay between attempts (not exponential, unlike API Call's
  backoff).
- **Permission gating**: none gates whether the node runs. The internal
  channel's `users`/`roles`/`teams`/`groups` fields are **recipient
  targeting** (who receives the notification, filtered to active users
  only), not an execution permission check on the node itself.
- **Risk tier**: high — Sends real outbound messages across email/Slack/Teams/SMS/WhatsApp/webhooks — genuine external communication that generally can't be undone once sent.

## Variable (`variable`)

Sets one or more named context variables to a literal value or an evaluated
expression (`{{...}}` interpolation, basic math operators).

- **Handler**: `lib/orchestrations/nodes/variable-node.ts`
- **Config** (`VariableNodeConfig`):
  | Field | Type | Required | Notes |
  |---|---|---|---|
  | `type` | `"variable"` | yes | |
  | `variables` | `Array<{name, value}>` | yes | `value` may be literal or expression |
- **Validation**: non-empty `variables` array; each entry needs a non-empty
  `name`; each `value` must not be `undefined`/`""`. A value is treated as an

- **Output**: `{ [name]: evaluatedOrLiteralValue, ... }` for every variable
  (dotted names create nested paths via `setVariablePath`).
- **Side effects**: none — pure context mutation.
- **Permission gating**: none.
- **Risk tier**: low — Pure in-memory context mutation.

## API Call (`api_call`)

Makes an outbound HTTP(S) request (including optional mTLS) with flexible
auth, body formats, path/query parameterization, and response field mapping,
with retry/backoff and a configurable failure strategy.

- **Handler**: `lib/orchestrations/nodes/api-call-node.ts`
- **Config** (`ApiCallNodeConfig` / `ApiCallAuthConfig`) — key fields:
  `apiUrl` (required, expression), `method` (required, default POST),
  `pathVariables`, `queryParameters`, `headers` (record or array form),
  `auth` (required; `none|api_key|bearer|basic|oauth2|custom_headers`, plus
  optional `mtls`), `bodyFormat` (`none|json|form_data|url_encoded|
  raw_text|xml|binary`), `requestBodyTemplate`, `formDataFields`,
  `urlEncodedFields`, `binaryBodyBase64`, `fileUploads`, `responseMapping` /
  `responseFieldMappings`, `outputVariableName` (default `"apiResult"`),
  `successStatusCodes` (default 2xx), `includeRawResponse` (default true),
  `timeout` (required, clamped [100,300000]ms), `retryAttempts` (required,
  clamped [0,10]), `retryDelayMs` (required, exponential-backoff base),
  `failureStrategy` (required: `stop|continue|alert`).
- **Validation**: `apiUrl` required; auth-type-specific required
  sub-fields (api_key name+value, bearer token, basic username, oauth2
  clientId+clientSecret when using tokenUrl, mTLS cert+key paths); JSON body
  must remain valid JSON after interpolation; binary body needs base64 or
  template; form-data file fields need `filePath`. Retries only for
  retryable failures (HTTP 408/429/5xx, or network/timeout errors); auth and
  JSON-parse errors are non-retryable.
- **Output (success)**: `{ requestMethod, requestUrl, httpStatusCode,
  responseHeaders, responseBody, parsedJson, rawResponse?,
  executionDurationMs, attempts, mappedFields, [outputVariableName]: {...} }`.
- **Output (failure, `failureStrategy=stop`)**: `{success:false, error}`.
- **Output (failure, `continue`/`alert`)**: `{success:true, output:{
  ...prior, apiCallFailed:true, error, errorDetails, ...}}`.
- **Side effects**: real outbound HTTP request (`fetch`, or Node
  `https.request` for mTLS); possible second HTTP call to an OAuth2 token
  endpoint; local file reads (`readFile`) for form-data files, file uploads,
  and mTLS cert/key/ca material; exponential-backoff retries.
- **Permission gating**: none. Secrets in headers are masked in logs
  (log hygiene, not an access-control gate).
- **Risk tier**: high — Arbitrary outbound HTTP(S) request, potentially with real credentials/mTLS, to any URL the config specifies.

## Database (`database`)

Uses the LLM to assess whether a natural-language database request is
answerable against a configured, tenant-scoped schema and, if so, generates
a single safe read-only `SELECT` query. **It generates and validates SQL but
does not execute it against any database** — every output path sets
`notExecuted:true`.

- **Handler**: `lib/orchestrations/nodes/database-node.ts`
- **Config** (`DatabaseNodeConfig`):
  | Field | Type | Required | Notes |
  |---|---|---|---|
  | `type` | `"database"` | yes | |
  | `schemaId` | `string` | TS-optional, runtime-required | |
  | `outputVariable` | `string` | no | default `"databaseQuery"` |
  | `userRequestVariablePath` | `string` | no | default `"userMessage"`, with several fallbacks tried |
  | `extractedInputVariablePath` | `string` | no | default `"extracted"` |
  | `additionalContextVariablePath` | `string` | no | |
  | `maxRows` | `number` | no | default 25, clamped [1,500]; force-appended as `LIMIT` |
  | `customInstructions` | `string` | no | appended to both LLM prompts |
  | `allowSelectStar` | `boolean` | no | default false |
  | `clarificationTimeoutMinutes` | `number` | no | default 15, floored at 1 |
- **Validation**: `schemaId` and a resolvable `companyId` required; the
  schema row must exist, be active, non-deleted, and belong to the resolved
  company/target app; an LLM readiness assessment runs first (pauses for
  clarification on chatbot triggers, else throws, if the request is
  under-specified); generated SQL must pass `validateSafeSelectQuery()` —
  single statement, starts with `SELECT`, denylist of DDL/DML keywords and
  comment/union/into patterns, must have a `FROM` clause, `SELECT *`
  rejected unless `allowSelectStar`; a heuristic fallback query is built by
  table/column name scoring if the LLM's SQL is empty/unparseable; a
  `LIMIT` is force-appended if absent.
- **Output (success)**: `{ [outputVariable]: {schemaName, databaseType,
  generatedQuery, sqlValidation:{valid:true,mode:'select_only'},
  generationMeta, capturedInput, reasoning, notExecuted:true} }`.
- **Output (paused)**: clarification-style pause with a partial payload
  (also `notExecuted:true`).
- **Output (failure)**: `{success:false, error, output:{databaseNodeError:
  {message, notExecuted:true}}}`.
- **Side effects**: one DB read (schema metadata, tenant-scoped); **two**
  LLM calls per execution (readiness assessment + SQL generation). No
  connection to, or execution against, the target application's actual
  database anywhere in this handler.
- **Permission gating**: none role-based; tenant isolation via
  `companyId`/`targetAppId` scoping on the schema lookup, not a user
  permission check.
- **Risk tier**: medium — Never executes SQL itself (notExecuted:true always), but generates real SQL against tenant schema metadata that a downstream step (e.g. api_call) may go on to execute.

## File Parser (`file_parser`)

Parses a chat-attached file (referenced by a dotted context path) into plain
text, or — for CSV — structured row objects, pausing to ask the user to
attach a file if one isn't present.

- **Handler**: `lib/orchestrations/nodes/file-parser-node.ts`
- **Config** (`FileParserNodeConfig`):
  | Field | Type | Required | Notes |
  |---|---|---|---|
  | `type` | `"file_parser"` | yes | |
  | `sourceVariablePath` | `string` | yes | dotted path to `{id,name,fileType,storagePath,sizeBytes}` |
  | `extractMode` | `text\|structured` | yes | `structured` is CSV-only |
  | `outputVariable` | `string` | yes | |
- **Validation**: `sourceVariablePath`/`outputVariable` required; resolved
  value must look like an attachment reference (checks `sourceVariablePath`,
  then `${outputVariable}.attachment` — the shape the engine writes after a
  clarification resume) — if absent, pauses asking the user to attach a
  file rather than failing; a parser must exist for the file type; structured
  mode throws for any non-CSV file type.
- **Output (text)**: `{ [outputVariable]: joinedPageText,
  [outputVariable+"Meta"]: {fileName, fileType, pageCount} }`.
- **Output (structured)**: `{ [outputVariable]: parsedCsvRows,
  [outputVariable+"Meta"]: {fileName, fileType, rowCount} }`.
- **Output (paused)**: clarification asking for an `attachment`.
- **Side effects**: reads file bytes via `getStorageProvider().get_file()`;
  parses via `getDocumentParser(fileType).parse()`; ships its own hand-rolled
  RFC4180-aware CSV row parser directly in this file (no external dependency
  added).
- **Permission gating**: none at node level. Enforced elsewhere:
  `node-compatibility.ts` lists `file_parser` as an `INTERACTIVE_NODE`,
  rejected at the orchestration level on automated triggers
  (schedule/email/http_api) since there's no live chat attachment to read.
- **Risk tier**: low — Read-only access to a chat-attached file already in the tenant's own storage.

## For Each (`for_each`)

Iterates an array from context, running one of a fixed allow-list of body
node types once per item, collecting per-iteration results.

- **Handler**: `lib/orchestrations/nodes/for-each-node.ts`
- **Config** (`ForEachNodeConfig`):
  | Field | Type | Required | Notes |
  |---|---|---|---|
  | `type` | `"for_each"` | yes | |
  | `sourceVariablePath` | `string` | yes | path to the array to iterate |
  | `itemVariableName` | `string` | yes | per-iteration binding name, default `"item"` |
  | `maxIterations` | `number` | yes | soft cap — see validation |
  | `continueOnItemFailure` | `boolean` | yes | default true unless explicitly false |
  | `bodyNodeType` | `api_call\|notification\|ai_extraction\|variable\|data_formatter` | yes | excludes interactive-only node types |
  | `bodyConfig` | union of those 5 configs | yes | |
  | `outputVariable` | `string` | yes | default `"loopResults"` |
- **Validation**: `sourceVariablePath`/`outputVariable`/`bodyNodeType`
  required; source must resolve to an array; **`maxIterations` is clamped to
  [1, 500] (`HARD_ITERATION_CEILING`) regardless of the configured value** —
  a hard cap independent of user config, because each iteration can trigger
  a real side effect (API call, notification, LLM call) per item; excess
  items beyond the clamp are silently truncated (`truncated:true` in meta).
- **Output**: `{ [outputVariable]: Array<{index, item, success, output?,
  error?}>, [outputVariable+"Meta"]: {totalItems, processedItems, succeeded,
  failed, truncated} }`. Only top-level precondition failures fail the node;
  individual item failures don't (unless `continueOnItemFailure=false`,
  which stops the loop early but still returns `success:true`).
- **Side effects**: delegates each iteration to the matching body-node
  executor, inheriting whatever side effects that type has (HTTP calls,
  notification sends + DB writes, LLM calls), repeated up to the clamped
  iteration count.
- **Permission gating**: none. Not listed as an `INTERACTIVE_NODE` in
  `node-compatibility.ts`, so usable with automated triggers too — consistent
  with its body-type allow-list excluding the interactive-only node types.
- **Risk tier**: high — Multiplies whatever side effects its body node type has (up to 500x) — inherits and amplifies the risk of api_call/notification, its two highest-risk allowed body types.

## AI Planner (`ai_planner`) — structural marker, admin/designer-only

Marks an orchestration as the drafting entry point that chat users land on
when they ask for something new: AI Planner (`lib/orchestrations/planner/agent.ts`'s
`PlannerAgent`) first tries to match an existing, admin-approved
orchestration to their request, and if nothing matches, drafts a new one for
admin approval. The node itself never executes any real logic — the
conversation runs entirely outside this graph, driven purely by
`companyId`/`targetAppId`.

**Deliberately excluded from `config/node-catalog.json` and
`config/planner-tools.json`** — this node type is never something the
drafting LLM should emit into a user-requested plan; it's placed manually by
an admin in the designer. Adding it to either of those files would let
`scripts/validate-planner-tools.mjs` fail or let a drafted plan nonsensically
reference itself.

- **Handler**: none — inline in `engine.ts`'s `executeNodeByType()`
  `"ai_planner"` case, a trivial `{ success: true, output: {} }`.
- **Config** (`AiPlannerNodeConfig`):
  | Field | Type | Required | Notes |
  |---|---|---|---|
  | `type` | `"ai_planner"` | yes | |
  | `isDraftingEntryPoint` | `boolean` | yes | when true, this orchestration registers as THE drafting entry point for its trigger type in its (company, target app) scope |
  | `matchConfidenceThreshold` | `number` | no | 0-1; only meaningful when `isDraftingEntryPoint` is true; falls back to `DEFAULT_MATCH_CONFIDENCE_THRESHOLD` (0.75) |
- **Validation**: `publishOrchestration()` rejects a graph with more than one
  `ai_planner` node, and — when checked — enforces at most one checked
  `ai_planner` node per (`company_id`, `target_app_id`, trigger type) via a
  pre-write check plus a partial unique index
  (`orchestrations_one_ai_planner_drafting_entry_per_scope`, migration
  `137_ai_planner_node.sql`). A graph containing an `ai_planner` node
  (checked or not) satisfies the "must have at least one end node"
  publish requirement on its own.
- **Output**: always succeeds, empty output.
- **Side effects**: none in the graph itself. When checked and published,
  writes `orchestrations.ai_planner_drafting_trigger_type`, which is what
  `app/api/chatbot/orchestrations/route.ts` and `matching.ts`'s
  `getEffectiveMatchConfidenceThreshold` read.
- **Permission gating**: none at node level; always compatible with every
  trigger type (`node-compatibility.ts`), same as `trigger`/`end`.
- **Risk tier**: low — structural marker with no side effects of its own.

## End (`end`) — pseudo-finish node

Assembles the orchestration's final response (selected output variables,
optional per-node response log, and an optional user-facing display
message/table/JSON) and always completes the execution successfully.

- **Handler**: none — inline in `engine.ts`'s `executeNodeByType()` `"end"`
  case via the private `buildEndNodeOutput()` method.
- **Config** (`EndNodeConfig`):
  | Field | Type | Required | Notes |
  |---|---|---|---|
  | `type` | `"end"` | yes | |
  | `displayMessage` | `boolean` | no | whether to render `message` as the final chat answer |
  | `message` | `string` | no | `{{...}}`-interpolated template |
  | `displayMode` | `text\|table\|json` | no | default `"text"` |
  | `displayDataPath` | `string` | no | path resolved for table/json display data |
  | `displayColumnPaths` | `string[]` | no | optional ordered table columns |
  | `outputVariables` | `string[]` | no | resolved into `selectedOutputs` |
  | `responseVariablePath` | `string` | no | default `"finalResponse"` |
  | `includeNodeResponses` | `boolean` | no | includes full per-node output log if true |
- **Validation**: none — every field optional with a safe default; this
  node cannot fail.
- **Output**: always succeeds. Sets `context[responseVariablePath] = {
  executionId, orchestrationId, completedAt, selectedOutputs,
  nodeResponses? }` and `context._chatbot = {..., finalAnswer,
  finalResponsePath, display?}`.
- **Side effects**: none — pure in-memory context assembly.
- **Permission gating**: none.
- **Risk tier**: low — Pure in-memory finalization; cannot fail or produce side effects.

## Surprising findings

1. **`workflow.outputMapping` is dead config.** `WorkflowNodeConfig`
   declares `outputMapping?: OutputMappingField[]`, and
   `workflow-node.ts`'s local `mapWorkflowOutput()` helper even accepts a
   second `outputMapping` parameter — but every call site in the handler
   invokes `mapWorkflowOutput(result)` with only one argument. The
   configured output mapping a user sets up in the UI is never read or
   applied at runtime.
2. **`database` node never touches the target database.** Despite the name
   and despite validating/generating real SQL against a real schema, the
   handler's only DB access is a metadata read of
   `target_app_database_schemas`; the generated `SELECT` is returned as data
   (`notExecuted:true` on every path) and never executed. It's a SQL
   *generator*, not a query executor.
3. **`IOrchestrationNode` (the plugin interface in
   `shared/orchestrationTypes.ts`, with `validate/execute/serialize/
   deserialize/renderProperties`) is declared but never implemented
   anywhere in the codebase** (`grep` for the type name matches only its own
   declaration). All 14 node handler files are plain async functions with
   ad hoc signatures, not classes implementing that interface — there is no
   formal `validate()` method on any node; "validation" is inline
   required-field/format checks at the top of each `execute...Node()`
   function.
4. **`trigger` and `end` have no handler files** — both are handled
   entirely inline inside `engine.ts` (`executeNodeByType()`'s `trigger`
   case, and the private `buildEndNodeOutput()` method for `end`), unlike
   the other 14 types which each have a dedicated file in
   `lib/orchestrations/nodes/`.
5. **`data_capture.mode`** (`dom|ai|hybrid|comprehensive`) **is declared but
   never read** by `data-capture-node.ts` — the handler always does the same
   thing (inject an overlay; real capture happens client-side in the
   frontend player) regardless of which mode is configured.
6. **`human_approval.timeout` and `.escalationEmail` are declared but never
   used** in `human-approval-node.ts` — there's no timeout/escalation logic
   in this handler at all; if approval timeouts exist, they must be enforced
   elsewhere (not found in this file).
7. **Permission/role checks found by grep (`workflow-node.ts` and
   `notification-node.ts`) are not execution gates.** `workflow-node.ts`
   hard-codes `isAdminRole: true` when building a trusted server-side
   session for guided-workflow lookup (privilege elevation for internal use,
   not an access check). `notification-node.ts`'s
   users/roles/teams/groups resolution for the `internal` channel is
   **recipient targeting** — who gets notified — not a check on whether the
   node is allowed to run. This matches the expectation that per-node
   permission gating doesn't exist; the orchestration itself is gated at the
   trigger level via `ChatbotTriggerConfig.allowedRoles`/`allowedUsers`
   (enforced in `lib/orchestrations/chatbot-trigger-matcher.ts`).
8. **`api-node-types.ts`** (in the same `nodes/` directory) is confirmed to
   be a legacy/shared type-definitions file (`ApiNodeConfig`,
   `ApiNodeExecutionResult`, etc., keyed by numeric `id`/`orchestrationId`)
   with no `execute...` function and no relation to the current
   `api_call` `NodeType` — it is not dispatched by `engine.ts` and is not a
   node type in its own right, consistent with the task brief's note to
   treat it as a shared helper, not a 17th node type.
9. **Two node types can "succeed while failing."** `api_call`
   (`failureStrategy: continue|alert`) and `notification` (per-channel
   partial failure) can both return populated failure/error detail inside
   an `output` object while the top-level `success` flag differs — API Call
   reports `success:true` on a swallowed failure, Notification reports
   `success:false` but still returns full `channelResults` — the shapes are
   deliberately asymmetric and worth knowing when consuming their outputs
   downstream.
